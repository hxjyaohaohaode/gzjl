# 工资、统一补贴和两位小数修复

本次建立在已有老板自定义周期、完整工作簿、证据、审批、历史筛选和不可变导出功能上，修复计算及展示的一致性。没有新增数据库迁移，没有批量修改已确认历史账单。

## 已复现的金额问题

同名补贴由旧版本的 `daily` 生效区间折算切换成新版本的 `period_end` 全额计入时，旧计算会叠加两段：旧折算金额 + 新全额 168.19。30 天周期内的两种变更时间可以精确复现用户给出的 `177.533370` 和 `177.526492`。这不是只靠显示两位小数可以解决的问题。

新规则在周期结束时存在同名全额补贴的情况下，只采用该版本的全额补贴，替代同一周期前面版本中的同名折算补贴；两种案例的补贴均为 **168.19**。不同名称的真实补贴仍分别计算。同一版本的重复补贴名称及重叠方案区间会拒绝保存或计算，避免悄悄重复付款。

新增补贴默认“每期全额一次计入（统一补贴选此项）”。明确选择“按生效时长折算”的既有补贴仍保留折算业务规则，页面显示实际计入额、设定额和版本，不能把主动设置的折算偷偷变成全额。

## 工资计算与金额精度

- 实时预估和周期计算使用同一个版本化计算函数。历史工时按当时生效的单价及规则分段计算，后续设置的新时薪不会覆盖月初旧时薪。周奖励继续保留跨版本防重复和月界限规则。
- 工作秒数、休息扣除、重叠区间、已批准优先的整秒预算均保留；固定工资和折算补贴使用精确毫秒区间比例，避免各版本分别截断秒数造成遗漏。
- 工资、奖励和每项同名补贴分别汇总，再按十进制四舍五入保留两位小数；用确定性的尾差分配把分组金额还原到组成明细。报销和人工调整按每张单据四舍五入。最终金额由这些实际计入的分币金额相加形成，不对每段工时先舍入累积误差。
- `2866.920833 → 2866.92`；`168.189999 → 168.19`；`1.005 → 1.01`；负扣减 `-1.005 → -1.01`；舍入后的零不会显示 `-0.00`。大额金额不经过 JavaScript Number 或 Excel 浮点再转换。
- 数据库存储仍使用原有六位十进制列，新的正式组成、应计、调整和最终金额在分位以后均为零；保留原始值和舍入政策的审计追踪。工时真实计算继续使用秒，界面和交接 CSV 中的小时显示两位小数不能作为反推工资的计算源。
- 日薪方案同一天发生版本变更，仍只计一个日薪：采用当天有效已批准工作中最后一份生效方案的单价；只有待审工作时才使用待审预估方案。单价选择政策与方案版本写入计算追踪，历史日期仍按历史版本计算，不将多个版本的日薪重复相加。

## 页面、AI 和文件

薪资总览、工资明细、补贴、报销、变化额和币种合计统一显示两位小数。人工配置金额及报销输入按分输入。AI 获取的工资事实金额也使用两位小数，继续引用既有事实及版本，不自行重算工资。实时计算等式显式包含获批报销。

新生成的汇总 CSV、完整工作簿中的工资汇总、组成金额、单价和报销金额都采用两位小数十进制文字。Excel 保留完整工作提交单、证据、版本、详细计算追踪和长文本续页；数字小时列显示两位小数，来源秒数保留真实值。所有成员组成金额、分类金额和最终金额可相加核对。

已确认的交接批次仍重取原文件及原 SHA-256，不能把已经交给外部平台的文件静默换掉。未确认的旧规则账单明确提示点击“更新计算并查看”；旧金额不能直接确认导出。新计算版本为 `payroll-engine-v9-versioned-cent-reconciliation`。

## 部署后核对

更新代码后，在薪资页面选择老板指定的原周期，对尚未确认的账单点击“更新计算并查看”，核对统一补贴是否为 168.19、基础薪资与组成是否一致，再下载总览及工作明细。已有确认文件需要修正时，沿用已有审计更正及调整流程，不直接覆盖原交接文件。

本次自动验收使用全部迁移后的隔离数据库、正式 Fastify API、构建后的前端和本地测试对象存储。不声称已经写入 Render 业务数据库、重新审批真实记录或验证外部发薪平台的实际导入模板。
