# 薪资计算与结算

## 计算原则

薪资计算以 PostgreSQL 的已审核工时和版本化薪资方案为事实来源。金额计算在共享库中采用十进制字符串与 `BigInt` 的最小货币单位，不使用 JavaScript 浮点数；显示格式化只发生在最终界面或导出层。

每次计算都会保存：适用薪资方案版本、费率规则、工时版本、调整项、明细构成和输入哈希。之后即使规则被编辑，也可以解释某张工资单为何得出该金额。

## 周期状态

|状态|允许操作|含义|
|---|---|---|
|draft|配置、计算、复算|尚未锁定的周期|
|calculated|复核、调整、重新计算|已有本次计算快照|
|settled|生成工资单、导出、只读查看|已结算，不能直接复算|
|locked|只读、审计、发起更正|最终锁定，业务事实不可直接修改|

工资周期覆盖按真实时间区间切分的工时。休息区间从可支付区间中扣除；跨日、夜间、周末、节假日、加班等规则按优先级、叠加策略与规则版本计算。算法发现净时长和休息区间不一致、缺少生效方案或周期已锁定时会停止并给出冲突，而不会猜测金额。

## 结算与更正

结算前需要复核异常、待审核工时和人工调整。结算将工资单与明细快照固定，并锁定本周期内已批准工时。锁定后不允许静默修改；更正走申请、审核和“下期补发/扣回”的链路，确保历史工资单、审批和审计记录可复算。

已锁定记录只有原记录所属成员可以发起更正。申请会保存完整的拟议工时结构（开始/结束、休息、工作内容与结果、可见性、项目关联）和更正原因，原始锁定事实不会被覆盖。审核人必须拥有该工时对应组织单元或项目范围的 `work.review` 授权，且不能审核自己的申请；驳回需要写明审核说明。批准但不涉及金额时只形成审核结论；若审核人明确填入非零补发/扣回金额，服务端才会在原周期之后的首个开放周期创建调整，货币由该成员在目标周期的有效薪资方案决定。缺少原周期、开放周期或有效薪资方案时系统会拒绝操作，不会猜测金额或币种；每一步都写入审计日志。

## 操作检查清单

1. 确认组织时区、周期开始/结束边界和生效薪资方案。
2. 处理待审核、异常或冲突工时；不要将不确定工时直接当作已批准。
3. 运行计算，检查输入哈希、规则版本、明细与调整原因。
4. 获得授权后结算并锁定；导出的敏感字段仍遵循调用者 scope。
5. 定期做恢复演练，确保备份中的薪资快照、工时版本和审计日志可一起恢复。


## 补贴计入方式与报销

补贴方案的每一项保存 `distribution`：旧方案缺省为 `daily`，保留按生效区间折算的行为；`period_end` 项在周期期末按当时生效版本一次计入，不按天摊分。实时月度看板把不摊分项列在月末，不将其作为工作增长的训练数据。标准周期按月配置；自定义周期仍以该周期为折算范围。方案变更、分配方式及计款版本都保存在结算明细的 calculationTrace 中。

员工在薪资页独立创建报销草稿，再上传文件或添加链接、文字凭证。提交要求至少一项已核验且非私有的证据，未完成上传的文件会阻止提交。草稿和待审申请可以撤回；驳回后保留申请与凭证，新申请重新提交。审批由组织范围的 `payroll.settle` 权限控制，不允许申请人审批自己；普通工时审核权限不会自动获得报销权限。

批准时选择开放周期，校验申请人的有效薪资方案与币种，生成一条正数 payrollAdjustment。已有活动计算批次或已结算的周期不能加入新报销，需先取消未结算批次或选择其他开放周期。报销审批采用行锁与版本校验，防止重复入账；提交后凭证在服务层及数据库层冻结。工资计算保存前会复核调整项，避免并发获批的报销漏入快照。本月获批报销在个人看板独立显示并进入预估总额，不增加工时或训练未来薪资增长。周期锁定后申请显示已结算。

本次 schema 迁移为 `0012_hot_korg.sql`。部署新 API 前运行 `pnpm db:migrate`，确保报销表及证据冻结触发器已创建。
